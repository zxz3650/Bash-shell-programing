# 11-2. 결정적 출력과 성능 측정

작업 완료 순서는 CPU·디스크·스케줄러에 따라 달라진다. 학습자가 같은 입력으로 같은 보고서를 얻으려면 표시 순서를 따로 고정해야 한다. 성능 측정도 입력 크기와 실행 환경을 기록해야 비교가 가능하다.

{% hint style="info" %}
### 🧭 학습 목표

- 완료 순서와 보고서 순서를 분리한다.
- 공유 파일 쓰기의 경쟁을 설명한다.
- 직렬 결과와 병렬 결과를 비교한다.
- 병렬화가 느려지는 조건을 설명한다.
{% endhint %}

## 0. 학습 전 확인

한 파일에 append하면 여러 printf가 항상 한 행씩 온전히 기록되는가? 작은 파일 세 개를 병렬화하면 반드시 빨라지는가?

## 1. 결과 파일 소유권

각 작업에 하나의 결과 파일을 할당한다. 여러 작업이 같은 파일을 수정하면 쓰기 순서와 경계가 불안정해질 수 있다. 단일 작성자가 최종 병합을 담당하면 결과 구조를 검증하기 쉽다.

파일명 자체를 임시 결과 이름으로 사용하면 같은 basename이 충돌한다. 제공 예제는 입력 번호를 키로 사용한다. 원래 경로와 번호의 대응을 보고서 형식 설명에 기록한다.

## 2. 직렬·병렬 결과 비교

```bash
lab_dir=$(mktemp -d)
bash examples/parallel/run-workers.sh 1 \
    examples/log-report/fixtures/events.log \
    examples/log-report/fixtures/expected.tsv > "$lab_dir/serial.tsv"
bash examples/parallel/run-workers.sh 2 \
    examples/log-report/fixtures/events.log \
    examples/log-report/fixtures/expected.tsv > "$lab_dir/parallel.tsv"
diff -u "$lab_dir/serial.tsv" "$lab_dir/parallel.tsv"
```

diff가 아무것도 출력하지 않고 상태 0이면 같다. 결과가 같은 것을 먼저 확인한 뒤 실행 시간을 비교한다.

## 3. 측정 항목

| 항목 | 기록 이유 |
|---|---|
| 입력 파일 수·바이트 크기 | 작업량 통제 |
| 동시성 | 비교 변수 |
| 실제 경과 시간 | 사용자 체감 |
| CPU·디스크 상황 | 병목 설명 |
| 실패 수·결과 비교 | 정확성 보장 |

time 명령의 출력 형식은 플랫폼과 셸에 따라 다르다. 같은 도구와 같은 환경으로 여러 번 측정하고 첫 실행의 파일 캐시 영향을 구분한다.

## 4. 빨라지지 않는 이유

작업이 너무 작으면 프로세스 생성 비용이 더 크다. 하나의 디스크가 병목이면 병렬 읽기가 오히려 경쟁을 만든다. 배치 방식에서는 가장 느린 작업이 다음 배치를 기다리게 한다. 부하가 증가했다고 처리량도 증가하는 것은 아니다.

## 5. 재시도와 중복

실패 작업을 다시 실행하면 같은 출력에 두 번 추가되지 않아야 한다. 작업 번호별 파일을 새로 만들거나 교체하는 정책을 사용한다. 비멱등 작업을 무조건 재시도하지 않는다.

## 🧪 직접 해보기

1. 동시성 1·2·4에서 동일 결과를 확인한다.
2. 작은 파일과 큰 파일이 섞인 배치의 완료 시간을 비교한다.
3. 작업 하나를 실패시키고 최종 결과가 최종 파일로 저장되지 않는지 확인한다.

### 해설

빠르다는 결론은 실제 측정이 있어야 한다. 교재는 특정 성능 향상률을 약속하지 않는다. 비교표에는 측정값과 검증 통과 여부를 함께 적는다.

## ✅ 완료 기준

- [ ] 직렬·병렬 결과가 동일하다.
- [ ] 출력 순서가 완료 순서에 의존하지 않는다.
- [ ] 성능 결론에 입력·환경·실패 수가 기록돼 있다.
