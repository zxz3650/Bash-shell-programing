# 11-3. 웹 로그 분석과 제한된 배치 처리

터미널 예제는 [공통 실습 준비](../examples/security-labs/README.md)를 먼저 수행합니다. 노트북은 Setup부터 실행합니다.

## 보안 질문과 목표

“로그인 실패·관리 경로 탐색·의심 파일 접근이 어떤 흐름을 이루는가?” Apache/Nginx 로그 형식을 먼저 확인하고 요청·상태·주소·시간을 구분합니다. 여러 파일을 처리할 때는 11장의 작업 수 제한과 실패 회수를 적용합니다. 실제 요청이나 스캔을 보내지 않고 합성 로그만 분석합니다.

## 필드를 먼저 확인하기

제공 access.log는 combined 형태의 교육용 로그입니다.

```text
192.0.2.10 - - [10/Sep/2026:09:01:00 +0900] "POST /login HTTP/1.1" 401 120 "-" "CourseBrowser/1.0"
```

주소, identity/user 자리, 시각·시간대, 인용된 요청, 상태, 바이트 수, Referer, User-Agent 순서입니다. 실제 LogFormat/log_format은 사용자 정의가 가능하므로 이 위치가 항상 같다고 가정하지 않습니다. 프록시 환경의 주소가 최종 사용자 주소인지도 설정과 신뢰 경계를 확인합니다.

## 파이프라인으로 요청과 상태 읽기

```bash
awk -F '"' '{split($3, status, " "); print $2 "|" status[1]}' "$COURSE_DATA/access.log"
```

```text
POST /login HTTP/1.1|401
POST /login HTTP/1.1|401
POST /login HTTP/1.1|401
GET /health HTTP/1.1|200
GET /uploads/report.txt HTTP/1.1|200
GET /admin HTTP/1.1|404
```

따옴표를 기준으로 요청 부분과 상태 부분을 나눕니다. 제공 자료에는 이스케이프된 따옴표나 변형 요청이 없다는 전제가 있습니다. 실제로는 서버가 기록한 이스케이프 규칙·JSON 형식·누락 필드를 처리하는 파서가 필요합니다. 파싱 실패 행을 버리지 말고 별도 계수합니다.

## 상태는 공격 결과가 아니다

401은 인증 필요/실패 문맥을, 404는 찾지 못한 자원을 나타내지만 애플리케이션 설계에 따라 의미가 달라집니다. 200은 요청 처리 상태이며 악성 코드 실행이나 업로드 성공을 증명하지 않습니다. `/uploads/report.txt`는 단지 접근 경로입니다. 파일 생성·내용·웹 서버 실행 설정·프로세스·애플리케이션 로그를 더 봐야 합니다.

## 가설별 추가 조사

| 가설 | 로그에서 볼 특징 | 추가 근거와 오탐 |
|---|---|---|
| 로그인 무차별 시도 | 같은 인증 경로의 반복 실패·계정/시간 패턴 | 사용자 실수·자동 재시도, 앱 인증 로그 필요 |
| 스캐닝 | 여러 경로·짧은 간격·404 증가 | 모니터링·링크 검사·승인 진단 |
| Path Traversal 시도 | 비정상 경로 구문·보안 장비 경보 | 정규화·인코딩·실제 파일 접근 결과 |
| SQL Injection 시도 | 비정상 입력 패턴·DB/앱 오류 | 원문 요청·파라미터 문맥·DB 감사, 문자열만으로 확정 불가 |
| WebShell 접근 의심 | 예상 밖 업로드 경로·후속 실행/통신 | 정상 문서 접근, 파일·프로세스 증거 필요 |
| Exploit 시도 | 특정 취약 기능 관련 경보·오류 | 실제 버전·도달 경로·후속 영향 |
| 의심 User-Agent | 기준선 밖 이름·도구 표식 | 쉽게 변경 가능, 정상 자동화 반례 |

이 표는 탐지 가설을 위한 것이며 공격 페이로드나 재현 절차는 제공하지 않습니다. Referer와 User-Agent는 신뢰할 수 있는 신원 증명이 아닙니다. 원문 URI를 여러 번 디코딩하면 본래 의미가 달라질 수 있으므로 원문과 각 변환 단계를 보존합니다.

## Red / Blue 관점

공격자는 웹 표면과 인증 동작을 이해하려 할 수 있습니다. 분석가는 요청 패턴과 실제 영향 사이의 증거를 연결합니다. 웹 접근 로그 → 앱 인증/오류 → 업로드 파일·프로세스 → 네트워크 기록 순으로 확인하고 정상 모니터링과 승인 진단을 배제합니다. 보존·접근 제한·보안 업데이트·입력 검증·인증 보호는 확인한 원인에 맞춰 제안합니다.

### Bash Point — 동시 실행과 완료는 별개

실습은 auth.log와 access.log의 줄 수를 별도 작업으로 계산합니다. `$!`로 PID를 받고 wait로 종료 상태를 회수합니다. 출력은 작업별 파일에 쓰고 고정 순서로 읽습니다. 여러 프로세스가 한 파일에 동시에 쓰면 행이 섞일 수 있습니다.

작업 수는 이 실습에서 2개로 제한합니다. 운영 증거가 저장된 디스크에 병렬 처리를 무작정 늘리면 I/O 부하와 일관성 문제가 생길 수 있습니다. 기존 11-1·11-2의 제한된 worker와 직렬/병렬 결과 비교를 적용합니다. 빠른 처리보다 누락·오류를 설명할 수 있어야 합니다.

## 실습·예상 결과

ch11.sh에서 요청 6행을 읽고 401=3, 200=2, 404=1을 확인합니다. 두 로컬 작업 결과는 auth=5행, access=6행입니다. 외부 주소에 접속하지 않습니다.

## 질문과 완료 기준

1. 401 세 건을 계정 세 개의 실패라고 결론 내릴 수 있는가?
2. 200 두 건을 공격 성공으로 세면 왜 틀리는가?
3. 인용된 필드의 변형이 생기면 어떤 테스트를 추가할 것인가?
4. 부분 실패 작업을 전체 성공으로 보고하지 않았는가?

형식 전제·계산·정상 반례·추가 자료를 제출하면 완료입니다. 다음 12장은 지금까지의 결과를 하나의 조사 보고서로 통합합니다.
