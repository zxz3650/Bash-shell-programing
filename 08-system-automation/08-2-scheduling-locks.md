# 08-2. 비대화형 실행·예약·중복 실행 방지

터미널에서 성공한 스크립트도 예약 실행에서는 실패할 수 있다. 작업 디렉터리, PATH, 환경, 터미널 존재 여부가 달라지기 때문이다. 예약 도구를 설정하기 전에 제한된 환경에서 직접 재현한다.

{% hint style="info" %}
### 🧭 학습 목표

- 비대화형 실행의 환경 차이를 재현한다.
- cron과 systemd timer의 책임을 구분한다.
- 작업 중복과 잠금 수명을 설명한다.
- 실제 스케줄 등록 전 검증 항목을 정한다.
{% endhint %}

## 0. 학습 전 확인

예약 시 .bashrc의 alias가 존재하는가? 앞 실행이 끝나기 전에 다음 실행이 시작되면 보고서는 어떻게 되는가?

## 1. 최소 환경에서 확인

```bash
env -i PATH=/usr/bin:/bin bash --noprofile --norc -c '
    printf "cwd=%s\n" "$PWD"
    command -v bash
    command -v awk
'
```

Homebrew 설치 도구처럼 별도 경로의 명령은 보이지 않을 수 있다. 필요한 경로는 배포 설정에 명시한다. 사용자 입력을 기다리는 read, sudo 암호 요청, 대화형 alias에 의존하지 않는다.

## 2. 예약 설정 읽기

다음은 형식 설명용이며 실제 설치 경로로 바꾼 뒤 등록해야 한다. 교재 코드는 자동으로 스케줄을 등록하지 않는다.

```cron
SHELL=/bin/bash
PATH=/usr/bin:/bin
0 * * * * /opt/course/bin/report.sh >> /opt/course/logs/schedule.log 2>&1
```

매시 0분 실행이다. 디렉터리와 권한은 미리 준비해야 한다. cron의 환경·시간대·퍼센트 처리 규칙 등은 배포판 매뉴얼을 확인한다. 실행 스크립트 안에 업무 로직을 두면 cron 줄의 복잡한 인용을 줄일 수 있다.

## 3. systemd 개념

| 구성 | 책임 |
|---|---|
| service | 사용자·명령·작업 위치·시간 제한 |
| timer | 언제 service를 시작할지 |
| journal | 실행 로그와 실패 조사 |

WSL과 컨테이너에서는 systemd 활성화 여부가 다를 수 있다. 단순 시간 간격뿐 아니라 실패 관찰과 실행 사용자, WorkingDirectory를 함께 정한다.

## 4. Linux flock 예제

```bash
# Linux, util-linux flock 필요. 같은 task_dir를 공유하는 실행끼리 잠금.
task_dir=${TASK_DIR:?set TASK_DIR to the course task directory}
(
    flock -n 9 || exit 1
    printf 'exclusive section\n'
) 9> "$task_dir/report.lock"
```

디스크립터 9가 열려 있는 동안 잠금이 유지된다. 잠금 파일이 존재하는 것과 잠금이 잡힌 것은 다르다. 실행마다 서로 다른 임시 잠금 경로를 만들면 중복 방지 효과가 없다. 작업 중 잠금 파일을 삭제하면 새 inode에 별도 잠금이 생길 수 있으므로 제거하지 않는다.

## 5. 실패와 재시도

입력 형식 오류를 반복 재시도해도 해결되지 않는다. 일시적 오류만 제한된 횟수와 간격으로 재시도한다. 보고서 덮어쓰기·중복 전송 같은 부수 효과가 있다면 재시도 전에 멱등성과 충돌 정책을 확인한다.

## 🧪 직접 해보기

1. 일반 터미널과 env -i 환경에서 도구 경로를 비교한다.
2. 같은 잠금 경로로 두 실행을 겹쳐 하나만 진입하는지 확인한다.
3. 실패했을 때 운영자가 확인할 로그 위치와 상태를 문서화한다.
