# 12-2. 프로젝트 B: 로컬 스냅샷과 최종 평가

로컬 시스템의 상태를 읽어 보고서·실행 로그·체크섬으로 보존한다. 시스템마다 결과가 달라지므로 특정 PID나 디스크 사용량을 정답으로 삼지 않는다. 수집 구조와 오류 처리, 출처와 시점을 평가한다.

{% hint style="info" %}
### 🧭 프로젝트 목표

- 수집 항목별 성공·실패·건너뜀을 기록한다.
- 결과와 로그를 제한된 권한으로 저장한다.
- 체크섬을 다시 검증한다.
- 개인 정보가 포함된 출력의 공유 범위를 정한다.
{% endhint %}

## 0. 실습 경로

[노트북 08](../jupyter-book/labs/08-capstone-triage-collector.ipynb)을 위에서 아래로 실행한다. 제공 노트북은 기본 수집기이며 아래 최종 요구사항은 학생 확장 과제다. 실행 결과에는 자신의 호스트·사용자·프로세스 정보가 포함될 수 있어 제출본은 검토 후 공유한다.

## 1. 수집 항목과 의미

| 항목 | 의미 | 검증 |
|---|---|---|
| 호스트·OS | 환경 식별 | 비어 있지 않음 |
| UTC 시작·종료 시각 | 관찰 구간 | 형식·순서 |
| 프로세스 목록 | 해당 시점의 실행 상태 | 필드·수집 상태 |
| 디스크 상태 | 파일시스템 사용 현황 | 명령 성공·출력 존재 |
| 로컬 소켓, 선택 | 로컬 수신 상태 | 도구 없음은 skipped |
| 체크섬 | 수집 후 내용 변경 확인 | 재계산 일치 |

스냅샷만으로 침해 여부를 확정하지 않는다. 관찰한 사실과 추가 확인이 필요한 해석을 구분한다.

## 2. 결과 구조 설계

```text
run-id/
├── manifest.tsv       항목·상태·상대 경로
├── system.txt         OS와 기본 정보
├── processes.txt      프로세스 목록
├── collection.log     시작·종료·진단
└── SHA256SUMS         최종 데이터 파일 해시
```

위 구조는 확장 과제의 목표다. 체크섬 파일 자체를 자기 목록에 포함하지 않는다. 로그를 해시한 뒤 추가 기록하면 검증이 실패하므로 기록 종료 시점과 해시 생성 순서를 정한다.

## 3. 처리 순서

1. 옵션·출력 경로를 검증한다.
2. dry-run이면 계획을 표시하고 종료한다.
3. umask 077과 새 실행 디렉터리를 사용한다.
4. 필수 항목을 수집하고 상태를 manifest에 기록한다.
5. 선택 도구가 없으면 skipped로 남긴다.
6. 수집 로그를 닫은 뒤 체크섬을 생성한다.
7. 체크섬을 검증하고 완료 여부를 알린다.

필수 항목 실패·선택 항목 없음·전체 성공을 구분한다. 작업이 실패했을 때 부분 결과를 별도 파일에 보관할지 폐기할지 정한다. 미완성 결과가 최종 보고서로 저장되지 않도록 한다.

## 4. 시험 시나리오

| 사례 | 확인할 결과 |
|---|---|
| 정상 환경 | 필수 항목·체크섬 존재 |
| 선택 도구 없음 | skipped, 이유 기록 |
| 기존 출력 경로 | 충돌 정책 준수 |
| dry-run | 파일 변경 없음 |
| 중간 실패 | 실패한 작업을 complete(완료)로 표시하지 않음 |
| 데이터 파일 변경 | 체크섬 실패 |

실제 시스템 설정을 망가뜨려 오류를 만들지 않는다. 선택 명령 이름을 테스트용 없는 이름으로 교체하거나, 테스트가 만든 출력 경로를 사용한다.

## 5. 평가 루브릭

| 영역 | 배점 | 근거 |
|---|---:|---|
| 용어·실행 모델 | 15 | 인수·프로세스·상태 설명 |
| 데이터 정확성 | 25 | 구조·집계·체크섬 |
| 실패와 원본 보존 | 25 | 오류·재실행·중단 검증 |
| 실습 재현성 | 20 | 환경·입력·테스트 명령 |
| 문서와 설명 | 15 | 입출력 형식·출처·한계·설계 이유 |

보안 용어를 많이 나열하는 것보다 실제 수집 결과와 실패 처리의 근거를 평가한다.
