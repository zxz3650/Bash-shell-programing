# 12-3. Capstone — Linux 조사 자료를 보존하고 근거 있는 보고서 만들기

## 사건 시나리오

lab-web-01의 09:00~10:00 KST 자료 일부가 전달됐습니다. 인증 실패 뒤 공개키 성공이 있고, collector 서비스의 승인 정보가 확인되지 않습니다. 웹 로그에도 로그인 실패가 있습니다. 목표는 침해를 무조건 증명하는 것이 아니라 **확인한 사실·가능한 가설·수집 한계·추가 확인을 분리하는 것**입니다.

자료는 모두 합성입니다. 외부 IP에 접속하지 않고 원본 파일을 실행하지 않습니다. 이 과제는 포괄적 포렌식 이미징이나 실제 사건 대응 권한을 부여하지 않습니다.

## 선수지식과 학습 목표

02장의 증거·시각, 03장부터 05장까지의 검색·파일·파이프라인, 06장부터 10장까지의 프로세스·권한·지속성·로그, 11장의 배치 검증을 통합합니다. 학생은 수집 사본을 기능별로 정리하고 누락을 숨기지 않는 Bash 도구와 분석 보고서를 제출합니다.

## 제공 자료와 조사 질문

| 자료 | 핵심 질문 | 제한 |
|---|---|---|
| provenance.txt | 출처·기간·시간대는? | 선택된 교육용 레코드만 포함 |
| passwd.sample·permissions.psv | 계정·권한이 기준선과 맞는가? | 실제 NSS·ACL 전체가 아님 |
| processes.psv·sockets.psv | 프로세스·서비스·목적지는? | 시점 제한, 패킷 내용 없음 |
| persistence.psv·service-review.txt | 자동 시작의 승인은? | drop-in 미수집 |
| auth.log·login-review.psv | 실패·성공·세션 관계는? | 로그인 요약은 바이너리 증거 아님 |
| journal-review.psv·audit.log | 부팅·서비스·실행 주체는? | Journal 요약·합성 Audit 한 이벤트 |
| access.log | 요청 패턴과 앱 동작은? | 앱·DB 로그·응답 본문 없음 |

## 초기 조사 흐름

1. 승인·사건 ID·수집 범위를 확인합니다.
2. 원본 목록·해시·시간대와 누락 자료를 기록합니다.
3. 작업 사본을 만들고 출처를 유지합니다.
4. 인증→세션→프로세스→서비스→통신을 같은 기간으로 비교합니다.
5. 계정·권한·자동 시작 설정을 정상 기준선과 비교합니다.
6. 웹 요청의 결과와 실제 호스트 영향은 별도 판단합니다.
7. 사실·가설·반례·추가 수집·완화 제안을 분리해 인계합니다.

실제 Live Response에서는 휘발성 정보의 가치, 수집 영향, 도구 신뢰성, 조직 승인에 따라 순서를 조정합니다. 원본에 도구를 설치하거나 의심 프로세스를 즉시 종료하는 순서를 기본값으로 삼지 않습니다.

## 함수로 책임 나누기

제공 triage-offline.sh는 다음 함수를 사용합니다.

```text
collect_system → 출처 메모
collect_users → 계정 사본
collect_processes → 프로세스 사본
collect_network → 소켓 사본
collect_persistence → 설정 검토 사본
collect_logs → 인증·로그인·Journal·Audit·웹 자료 사본
```

함수는 이미 수집된 고정 이름의 교육 자료를 복사합니다. 라이브 시스템 전체를 자동 수집하거나 공격 경로를 찾는 도구가 아닙니다. 분석과 수집을 분리해 자동 수집 성공을 자동 침해 판정으로 오인하지 않게 합니다.

## 도구 실행

저장소 루트에서 새 결과 디렉터리 이름을 사용합니다. 부모 임시 폴더 아래의 report는 아직 없어야 합니다.

```bash
lab_dir=$(mktemp -d) || exit 1
bash examples/security-labs/triage-offline.sh \
  -d examples/security-labs/data -o "$lab_dir/report" -n
bash examples/security-labs/triage-offline.sh \
  -d examples/security-labs/data -o "$lab_dir/report"
```

정상 출력은 `collection_status=complete`입니다. 이는 지정한 자료 복사·상태·해시 생성이 완료됐다는 뜻이며 사건의 전체 증거가 완전하다는 뜻이 아닙니다.

| 상태 | 의미 | 결과 취급 |
|---|---|---|
| 0 | 필요한 복사·기록 완료 또는 dry-run 검증 완료 | mode와 출처를 함께 확인 |
| 1 | 선택 자료 누락·복사/후처리 실패 | partial/불완전 결과로 검토 |
| 2 | 인수·필수 입력·출력 경로·환경 오류 | 실행 조건 수정 |

필수 provenance.txt와 auth.log가 없으면 결과 폴더를 만들지 않습니다. 선택 자료 누락은 manifest에 unavailable로 남깁니다. 기존 출력이나 심볼릭 링크 입력 항목을 거부합니다. 이 검사는 적대적인 동시 파일 교체까지 막는 OS 샌드박스가 아니므로 분석가는 통제된 사본을 사용해야 합니다.

## 산출물과 해시 검증

manifest.tsv는 범주·파일·복사 상태 12항목을 기록합니다. context.txt는 현재 복사 시각(KST)과 offline 출처를 표시합니다. SHA256SUMS는 복사 자료와 manifest/context의 내용 해시를 담고 자기 자신은 제외합니다. 마지막 COLLECTION_FINISHED는 해시 생성까지 끝난 뒤에만 생기며 해시 목록에는 포함되지 않습니다. 완료 표식·종료 상태·manifest를 함께 확인하고 최종 공유 전 해시 검증도 수행합니다. 표식 없는 중간 결과를 완료로 취급하지 않습니다.

Ubuntu에서는 결과 디렉터리에서 `sha256sum --check SHA256SUMS`를 사용합니다. macOS는 `shasum -a 256 --check SHA256SUMS`를 확인하거나 테스트의 Python 검증을 사용합니다. 단순 복사는 메타데이터 전체를 보존하는 포렌식 수집이 아닙니다.

## 분석 해설과 남겨야 할 질문

- SSH 실패는 3행, 공개키 성공은 1행입니다. 같은 주소의 실패 후 성공을 비밀번호 공격 성공이라고 단정하지 않습니다.
- UID 0 계정은 2개입니다. legacy-admin의 승인·생성·사용 이력은 추가 확인입니다.
- collector 서비스는 승인 정보가 없고 실행 경로의 그룹 쓰기가 검토 대상입니다. 이것만으로 권한 상승이나 지속성 설치자를 확정하지 않습니다.
- PID 520과 `.7:443`의 연결은 프로세스 문맥을 보여줍니다. 목적지 정당성·TLS·C2는 미확인입니다.
- Audit 6레코드는 id 실행 1이벤트입니다. auid1000/euid0은 권한 문맥이며 승인 여부는 별도입니다.
- 웹 401 세 건·200 두 건·404 한 건은 HTTP 상태 분포입니다. 호스트 실행 성공이나 파일 악성 여부와 동일하지 않습니다.

정상 배포·모니터링·관리자 작업을 대안 가설로 제시하고 어떤 자료가 이를 확인/반박할지 작성합니다. 모르는 정보를 보고서 빈칸으로 숨기지 말고 unknown과 이유를 적습니다.

## 실패 조건과 완료 기준

입력 원본 변경, 미수집을 0건으로 보고, 일부 실패를 전체 성공으로 보고, 실제 비밀정보 공개, 근거 없는 공격 성공 단정은 보완이 필요한 항목입니다. ch12.sh와 전체 보안 실습 테스트를 통과하고 보고서가 다음 7가지에 답하면 완료입니다: 왜 실행했는가 / 어느 필드를 봤는가 / 공격자에게 어떤 의미인가 / 방어자에게 어떤 의미인가 / 가능한 흔적은 무엇인가 / 어떤 로그로 확인하는가 / 어떻게 안전하게 반복할 것인가.

## Red Team ↔ Blue Team 사례 분석

### Capstone 역할 교대 — 하나의 자료 묶음, 두 개의 검토서

두 학생이 같은 합성 사본을 사용합니다. 한 명은 **Red Team 위험 검토자**로 목적·조건·영향 가설을 적고, 다른 한 명은 **Blue Team 조사자**로 실제 근거·반례·누락·개선을 적습니다. 이후 역할을 바꾸어 상대의 결론이 자료보다 앞서가는 부분을 찾습니다. 혼자 학습할 때는 두 열을 차례로 작성합니다.

| 연결 단계 | 종합 과제 |
|---|---|
| Goal / Boundary | 계정 접근·업무 도구 위임·서비스 통제라는 세 경계를 각각 설명 |
| Command / Observation | 05장 인증 집계, 06장 프로세스/소켓 조인, 07장 권한 검토, 10장 Audit 이벤트 연결 |
| System Change / Artifact | 로그인·실행·설정·파일의 현재 관찰과 과거 변경을 분리 |
| Log prerequisite | 출처·기간·KST·부분 수집과 실제 기록 기능의 공백을 명시 |
| Blue Team Investigation | 인증 성공·sudo·id·서비스·통신의 연결된 사실과 연결 미확인 부분을 구분 |
| Detection | 정상 작업·검토 필요·자료 부족 세 종류로 탐지 요구사항을 평가 |
| Mitigation | 근거가 있는 권한·구성·로깅 개선을 제안하고 보존·승인·복구 영향을 적음 |

### 제출할 사건 카드 세 개

| 카드 | Red Team 질문 | Blue Team 확인 자료 | 현재 결론의 상한 |
|---|---|---|---|
| C01 인증 | 인증·접근 정책의 경계는 적절한가? | auth.log·로그인 요약·키/장치 승인 | 실패와 공개키 성공 관찰, 비밀번호 공격 성공 미입증 |
| C02 권한 | 업무 도구 위임이 필요한 범위에 한정되는가? | 계정·권한 사본·sudo·Audit·정책/업무 문서 | id 권한 실행 관찰, 위임 정책 전체·승인 미확인 |
| C03 지속성·통신 | 서비스 구성과 목적지 통제가 적절한가? | 프로세스·소켓·서비스·Journal·변경 승인 | 서비스·연결 관찰, 악성 설치·C2 미입증 |

C02는 [GTFOBins 해설](../07-secure-scripting/07-4-gtfobins-review.md)의 **기능 / 권한 문맥 / 업무 범위 / 실행 근거** 구분을 적용합니다. 사건의 실제 sudo 정책은 제공되지 않았으므로 임의의 취약 정책을 만들어 보고하지 않습니다. tool-review.psv는 07장 별도 사고 훈련용 카드이며 이 사건 호스트의 추가 증거가 아닙니다. 수집기의 고정 12항목에도 포함되지 않습니다.

### 모범 답안의 형태

“09:03 KST에 analyst의 sudo id 메시지와 동일 시각의 auid1000/euid0 Audit 이벤트가 있다. 높은 권한의 id 실행과 부합한다. 업무 승인과 당시 정책 전체는 제공되지 않았다. 정책·변경 요청·세션 연결 자료를 추가 확인하고, 업무 범위를 넘는 위임이 확인되면 최소 권한으로 조정한다.”

이 문장은 관찰·의미·누락·다음 조치를 담지만 침해 성공을 꾸며내지 않습니다. 또한 09:05 collector 서비스가 앞선 로그인에 의해 시작되었다는 인과관계는 자료만으로 확정할 수 없으므로 별도 가설로 남깁니다.

### 역할별 채점

기존 100점 루브릭의 교차 분석·반례 25점을 다음과 같이 적용합니다: Red Team 목적·전제 8점, Blue Team 아티팩트·수집 조건 8점, 정상 반례·한계·탐지 평가 9점. 새로 25점을 더하는 것이 아닙니다. bash 테스트 통과만으로 이 점수를 자동 부여하지 않습니다.

**완료 기준:** 세 카드 모두 여덟 연결 단계를 작성하고, GTFOBins 미등재를 안전 판정으로 쓰지 않으며, 미수집과 사건 부재를 구분합니다. 상대 역할의 결론 한 개를 근거로 수정한 기록을 제출합니다. 명령 실행 성공이나 그럴듯한 공격 시나리오보다 검증 가능한 설명을 평가합니다.
