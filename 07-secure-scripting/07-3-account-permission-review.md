# 07-3. 계정·권한과 권한 상승 위험을 점검하기

터미널 예제는 [공통 실습 준비](../examples/security-labs/README.md)를 먼저 수행합니다. 실제 /etc/passwd 대신 제공 passwd.sample을 사용합니다.

## 질문과 목표

“누가 어떤 파일·서비스를 통제할 수 있고, 그 권한이 업무에 필요한가?” 실제 권한 상승을 수행하지 않고 계정·파일 권한·특수 비트·sudo·capability의 보안 경계를 이해합니다. 공격에 이용될 수 있는 조건과 이미 발생한 침해 증거를 구분하는 것이 목표입니다.

## 계정 파일 읽기

```bash
awk -F: '$3 == 0 {print $1, $3, $7}' "$COURSE_DATA/passwd.sample"
```

```text
root 0 /bin/bash
legacy-admin 0 /usr/sbin/nologin
```

/etc/passwd는 이름·암호 표식·UID·GID·설명·home·shell의 7개 필드입니다. x는 보통 shadow로 분리된 암호 정보를 가리키며 암호 자체가 아닙니다. /etc/shadow에는 민감한 암호 해시·노화 정보가 있으므로 기본 실습에서 수집하거나 공개하지 않습니다. 잠금 표식이나 nologin 하나만으로 모든 인증 경로를 차단한다고 단정하지 않습니다.

UID 0 계정 둘은 검토 필요 조건입니다. nologin은 특정 로그인 흐름의 셸 제약이지 UID 0 권한 자체를 없애지 않습니다. 승인된 예외인지·계정 생성 이력·실제 사용 흔적을 확인합니다. 실제 시스템은 getent·NSS·디렉터리 서비스를 통해 로컬 passwd 밖의 계정도 제공할 수 있습니다.

## 권한·소유자·특수 비트

| 항목 | 의미 | 조사 질문 |
|---|---|---|
| 일반 rwx | owner/group/other 접근 비트 | ACL·마운트·상위 디렉터리도 고려했는가? |
| SUID | 실행 시 파일 소유자 권한 관련 | 필요한 프로그램인가, 신뢰된 배포본인가? |
| SGID | 실행 그룹·디렉터리 그룹 상속 | 용도와 범위가 맞는가? |
| Sticky | 공유 디렉터리 항목 삭제·이름 변경 제한 | 쓰기 자체를 차단하는 것으로 오해하지 않는가? |
| Capability | root 권한 일부를 세분화 | 기능에 비해 과도한 권한인가? |

4755 passwd는 일반적으로 비밀번호 변경 기능을 위한 특수 권한 예입니다. 모든 SUID 파일을 악성 또는 취약하다고 표시하면 오탐이 됩니다. 실제 적용은 nosuid·no_new_privs·실행 파일 종류·환경 정책 등에 영향을 받습니다.

## 승인 VM의 제한된 조회

다음은 자신의 Ubuntu VM에서 경로와 목적을 정한 뒤 수행하는 선택 점검입니다. 시스템 설정을 바꾸지 않습니다.

```bash
find /usr/bin -xdev -type f -perm -4000
find /usr/bin -xdev -type f -perm -2000
getcap /usr/bin/ping
```

getcap은 설치되지 않았거나 결과가 없을 수 있습니다. capability 이름이 나왔다면 기능·패키지 기준선·설정 변경 이력을 확인합니다. 쓰기 가능한 서비스 실행 경로는 서비스 실행 계정·상위 디렉터리·ACL·변경 권한까지 검토해야 합니다. 위험을 확인하기 위해 파일을 교체하거나 권한을 부여하지 않습니다.

## 권한 상승 위험 검토표

| 영역 | 왜 경계 문제가 되는가 | 필요한 조건과 확인 | 탐지·완화 |
|---|---|---|---|
| sudo 정책 | 위임한 작업이 권한 경계 | 실제 허용 명령·인수·실행 사용자 | 최소 위임·정책 검토·인증 로그 |
| 쓰기 가능한 서비스 파일 | 낮은 권한의 변경이 서비스에 영향 | 실행 권한과 변경 권한의 교차 | 소유자·ACL·배포 통제·변경 기록 |
| PATH/환경 | 이름 탐색·설정이 실행에 영향 | 상대 경로·신뢰하지 못한 입력 | 명시 경로·제한 환경·입력 검증 |
| cron/systemd | 예약/부팅 동작에 설정이 영향 | 실행 주체·설정 수정 권한 | 기준선·승인 변경·Journal |
| 비밀정보 노출 | 인증 경계 훼손 가능 | 실제 권한·수명·노출 범위 | 최소 수집·접근 제한·폐기/교체 절차 |
| 커널/OS | 패치 상태에 따라 위험 | 정확한 배포 패키지·벤더 수정 | 권고 확인·검증된 업데이트 |

sudo 그룹 이름만 보고 허용 작업을 추측하지 않습니다. 승인된 환경에서 자기 계정의 `sudo -l`을 확인할 때도 인증·로그 기록과 비밀정보 노출을 고려합니다. 이 교안은 정책 검토를 다루며 우회·악용 명령이나 exploit 실행법은 제공하지 않습니다.

### Bash Point — 선택과 판정 분리

awk 조건은 점검 후보를 선택합니다. `review`는 사람이 조사할 목록이지 취약점 확정 플래그가 아닙니다. 함수로 자동화할 때도 `collect`·`compare`·`assess`를 나눠 관찰 실패와 정상 기준선 일치를 구분합니다.

## 실습과 기대 결과

ch07.sh는 실제 계정·파일 권한을 바꾸지 않고 합성 목록을 읽습니다. UID 0 계정 2개, 기준선 SUID 파일 1개, 검토 필요 파일 1개를 찾습니다. 출력은 `review_items=1 exploitation_proven=no`입니다.

## 분석 질문·완료 기준

legacy-admin의 승인을 어디서 확인할까? collector 그룹 쓰기가 어떤 업무상 필요일 수 있을까? 실행 사용자와 변경 권한을 모르는데 권한 상승 가능성을 확정할 수 있을까? 정상 예외·부족한 자료·완화 방안을 제출합니다. 실제 권한 변경이나 공격 성공 재현은 완료 조건이 아닙니다.

## Red Team ↔ Blue Team 사례 분석

### 사례: UID 0 계정과 쓰기 가능한 업무 파일

**Red Team 질문:** 식별된 계정·권한 예외가 업무 범위를 넘어서는 통제 가능성을 만드는가? UID 0 계정 둘과 그룹 쓰기 가능 파일 하나는 서로 다른 관찰입니다. 두 사실을 연결하는 실행·접근 조건 없이 하나의 권한 상승 경로로 단정하지 않습니다.

| 연결 단계 | 분석 내용 |
|---|---|
| Goal / Boundary | 계정·위임·파일 변경 경계의 과도한 권한 검토 |
| Command / Observation | awk로 UID 0과 권한 요약 읽기, 승인 VM에서는 범위를 정한 find/getcap 조회 |
| System Change / Artifact | 계정·그룹·비트·ACL·Capability·정책의 변경 가능 흔적. 현재 값은 변경 주체를 직접 보여주지 않음 |
| Log prerequisite | 계정 관리·Audit·정책 변경·패키지/배포 기록. sudo 로그는 모든 SUID 실행 기록이 아님 |
| Blue Team Investigation | legacy-admin의 생성·승인·사용 이력, collector 파일의 실행 주체와 수정 권한 비교 |
| Detection | 정상 기준선 밖의 권한 변경과 실제 사용을 별도 경보·조사 상태로 관리 |
| Mitigation | 예외 권한 재검토·업무와 배포 권한 분리·정책 변경 승인. 원본 보존 후 승인 절차로 수정 |

**반례와 해설:** passwd의 SUID는 정상 배포 기준선일 수 있습니다. nologin 설정은 특정 셸 로그인 경로를 제한하지만 UID 0 권한을 없애는 것이 아닙니다. 자동 보고서는 `review`를 `exploited`로 바꾸지 않습니다.

**제출 과제:** 계정 예외와 파일 예외를 별도 항목으로 작성하고, 각각 성립 조건·부족한 자료·정상 반례·완화를 적습니다. 다음 절의 [GTFOBins 검토](07-4-gtfobins-review.md)에서 정상 도구의 기능과 실행 권한 문맥을 비교합니다.
