# 01-4. 첫 조사 기록 실습

## 개요

앞 절에서 개별 명령과 판단 원칙을 배웠습니다. 이제 **고정된 교육용 자료의 해석**과 **자기 환경의 현재 상태 관찰**을 각각 수행합니다. 두 결과를 섞지 않고, 코드가 성공했다는 것과 분석 결론이 타당하다는 것을 따로 확인합니다.

## 학습 목표와 준비

- 명령 선택 이유·결과·오류·해석을 하나의 기록으로 남깁니다.
- 인용과 명령 치환을 사용하고 실패 상태를 보존합니다.
- KST와 원본 시각의 관계를 설명합니다.
- 정상 입력뿐 아니라 잘못된 인수·명령 실패·저장 충돌도 확인합니다.

선수 학습은 [01-1](01-1-first-observation.md)~[01-3](01-3-artifacts-and-reasoning.md)입니다. Bash 터미널은 저장소 루트에서 시작합니다. 설치가 필요하면 [02장](../02-bash-setup.md)을 먼저 수행합니다.

노트북 사용자는 [노트북 01](../jupyter-book/labs/01-when-to-use-bash.ipynb)을 위에서 아래로 실행합니다. 노트북에는 같은 교육용 자료와 관찰 도구가 포함되어 있어 실행 중 GitHub에서 추가 코드를 가져오지 않습니다. 기본 Python 커널의 `%%bash`를 사용합니다.

## 1. 작업 영역과 원본 구분

아래 준비 블록은 같은 터미널에서 실행합니다.

```bash
lab_dir=$(mktemp -d) || exit 1
umask 077
printf 'lab_dir=%s\n' "$lab_dir"
cat examples/first-observation/fixtures/case.txt
```

원본 입력은 저장소의 fixture, 결과 출력은 별도 lab_dir입니다. 원본 파일을 편집하거나 같은 경로에 결과를 저장하지 않습니다. `mktemp -d`는 새 디렉터리를 만들지만 운영체제 수준의 샌드박스는 아닙니다. 코드가 다른 경로를 수정하지 않는지 검토해야 합니다.

## 2. 고정 자료 읽기

출력 중 일부:

```text
source_type=synthetic
observed_at=2026-09-10T09:00:00+09:00
host=lab-ubuntu
uid=1000
group=sudo
configured_login_shell=/bin/zsh
observed_shell=bash
audit_coverage=unknown
```

이 목록은 관찰 항목을 설명하는 단순한 key=value 수업 형식입니다. 실제 Linux 인증 로그가 아닙니다. `source`로 실행하지 말고 데이터로 읽습니다.

### 분석 질문

1. 실제 사건 자료인가, 합성 자료인가?
2. 로그인 셸 설정과 실제 관찰한 셸이 다른 이유는 무엇인가?
3. sudo 그룹 소속으로 어떤 사실까지 확인했는가?
4. Audit 수집 여부를 모를 때 “추가 행위 없음”으로 결론 내릴 수 있는가?
5. 추가로 받아야 할 자료 두 가지를 제안하라.

기대 답변은 [예제 안내](../examples/first-observation/README.md)에 있습니다. 먼저 자기 답변을 작성한 뒤 비교합니다. 정상 관리 작업이라는 대안 가설도 남깁니다.

## 3. 자기 환경 관찰

```bash
bash examples/first-observation/observe-context.sh
```

교육용 출력 예:

```text
source_type=live_self
observed_at_kst=2026-09-10T09:00:00+0900
display_timezone=Asia/Seoul (UTC+09:00)
host=lab-ubuntu
os=Linux
kernel=6.8.0-lab
effective_uid=1000
effective_gid=1000
bash_version=5.2.21(1)-release
shell_pid=4200
shell_ppid=4100
process_pid_ppid_comm=4200 4100 bash
collection_status=complete
```

자기 환경의 값은 달라집니다. 필드의 존재·종료 상태·시간대·관찰 범위를 평가합니다. 프로세스 정보는 관찰 스크립트 자신의 Bash이며, 전체 프로세스 목록이나 SSH 로그인 세션 증거가 아닙니다.

### Bash Point — 작은 명령 묶음을 스크립트로 만들기

기준 구현에서 다음 부분을 찾습니다.

```bash
host_name=$(hostname) || exit 1
printf 'host=%s\n' "$host_name"
```

명령 치환으로 작은 값을 받아, 실패하면 종료하고, 고정된 형식 문자열로 표시합니다. 여러 줄의 코드를 무조건 외우는 것이 아니라 어느 줄이 수집·상태 검사·출력인지 표시합니다. 함수와 CLI 옵션 확장은 후속 장에서 학습합니다.

## 4. 새 결과만 저장하고 실패 확인

1단계에서 만든 lab_dir를 사용합니다. 아래 코드는 새 파일만 허용하며 오류는 화면에 표시합니다. `set -C`는 일반 파일 덮어쓰기를 막는 셸 옵션이지만 모든 적대적 파일시스템 변경을 막는 샌드박스는 아닙니다.

```bash
if (
    set -C
    bash examples/first-observation/observe-context.sh > "$lab_dir/context.txt"
); then
    printf 'saved: %s\n' "$lab_dir/context.txt"
else
    printf 'not complete: collection or saving failed\n' >&2
fi
```

한 번 더 실행하면 같은 결과 파일을 덮어쓰지 못합니다. 성공 문구가 아니라 파일 내용과 종료 상태를 확인합니다. 수집 실패 때 빈 파일이 만들어질 수 있으므로 파일 존재 자체도 성공 기준이 아닙니다. 완성된 결과만 최종 경로에 공개하는 방법은 [04-3](../04-file-io/04-3-streams-atomic-output.md)에서 다룹니다.

결과에는 호스트명·ID·프로세스 정보가 포함됩니다. GitHub에 그대로 커밋하지 않습니다. 노트북도 공개 저장소에는 실행 출력을 제거하고, 고정된 교육용 출력만 설명 셀에 넣습니다.

## 5. 정상과 실패를 각각 검증

```bash
bash tests/test-first-observation.sh
```

정상 실행은 명명된 검사마다 PASS를 출력하고 최종 성공 상태 0으로 종료합니다. 하나라도 기대와 다르면 FAIL과 0이 아닌 상태를 반환합니다. 검증 자료는 임시 폴더에만 생성하며 테스트 종료 시 그 폴더를 정리합니다.

| 사례 | 기대 결과 | 분석 의미 |
|---|---|---|
| 자기 환경 관찰 | 필요한 필드·KST 오프셋·상태 0 | 지정한 관찰 명령의 완료 |
| 불필요한 인수 | 사용법·상태 2 | 입력을 잘못 사용함 |
| 수집 명령 실패 | 진단·상태 1·완료 보고서 없음 | 데이터 부족, 이상 없음이 아님 |
| 시간대 불일치 | 진단·실패 | 잘못된 시각 표기를 방지 |
| 필수 출력이 비어 있음 | 실패 | 출력 없음과 정상 관찰 구분 |
| 기존 결과에 다시 저장 | 기존 내용 유지·실패 | 원본 또는 이전 결과 보존 |
| 공백이 있는 표식 | 하나의 값으로 유지 | 인수 경계 보존 |

테스트 대역은 테스트 안에서만 쓰는 임시 명령이며 시스템 명령을 바꾸지 않습니다. 실패를 재현하기 위해 실제 서버의 권한·시간대·프로그램을 변경하지 않습니다.

## 6. Bash를 선택한 이유 설명

이 실습의 핵심은 이미 설치된 명령을 순서대로 실행하고 상태를 확인하는 것입니다. 따라서 Bash가 적합합니다. 수백 종류의 로그 스키마·복잡한 시간 변환·관계형 데이터 분석으로 커지면 Bash는 실행 조정에 남기고 전용 파서나 Python으로 데이터 처리를 분리합니다.

노트북에는 기존의 작은 로그 집계와 도구 선택 연습도 유지했습니다. 함수 예제는 실행 결과를 읽는 선택 학습이며 이 장에서 모든 함수 문법을 암기하는 과제는 아닙니다.
