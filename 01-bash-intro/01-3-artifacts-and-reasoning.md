# 01-3. 행위·흔적·판단의 구분

## 개요

`uname`을 실행한 기록이 있다고 공격이라고 할 수 있을까요? 정상적인 시스템 점검과 공격자의 환경 확인은 같은 도구를 사용할 수 있습니다. 따라서 명령 이름을 찾는 것과 사건을 판단하는 것은 다른 작업입니다.

## 학습 목표

- 행위·아티팩트·로그·분석 결과의 차이를 설명합니다.
- 관찰 사실과 해석을 나누어 적습니다.
- 공격자 목적과 방어자 조사 질문을 같은 자료에 연결합니다.
- 기록되지 않은 행위와 수행되지 않은 행위를 구분합니다.

## 1. 서로 다른 네 가지 정보

| 구분 | 의미 | 예 |
|---|---|---|
| 행위 | 실제로 일어난 동작 | OS 정보를 읽는 명령 실행 |
| 아티팩트 | 분석에 활용할 수 있는 흔적이나 자료 | 프로세스 메타데이터·파일·구성 |
| 로그 | 특정 기록 기능이 남긴 이벤트 | 감사 이벤트·서비스 메시지 |
| 분석 결과 | 자료를 해석하여 만든 설명 | 정상 점검과 시간·계정이 일치함 |

명령 stdout은 조사자가 새로 만든 관찰 자료일 수 있습니다. 이미 존재하던 사고 당시 로그와 출처가 다릅니다. 지금 실행한 `id`는 지금의 권한이며 어제 로그인한 사람의 권한을 직접 증명하지 않습니다.

## 2. 공격자 목적에서 탐지까지 연결하기

| 단계 | 환경 정보 확인 사례 |
|---|---|
| Technique | System Information Discovery |
| Attacker Goal | OS·실행 환경을 이해하려는 목적 |
| Linux Command | 예: `uname`, `hostname` |
| System Change | 설정 변경이 없어도 실행 프로세스와 관찰 활동이 발생 |
| Artifact | 수집된 프로세스 메타데이터·조사자가 저장한 출력 등 |
| Log | 기록 설정이 갖춰진 경우의 감사·실행 관련 이벤트 |
| Investigation | 주체·부모·시각·승인 작업·주변 행위 확인 |
| Detection | 맥락과 여러 자료가 일치할 때 조사 후보로 분류 |
| Mitigation | 접근 통제·최소 권한·필요한 로깅과 보존 정책 |

이 연결은 모든 환경에서 흔적이 반드시 남는다는 약속이 아닙니다. MITRE ATT&CK의 [System Information Discovery, T1082](https://attack.mitre.org/techniques/T1082/)는 관련 행위 분류를 제공합니다. 정상 관리자가 명령을 실행했다는 이유만으로 공격 기술이 관찰되었다고 보고하지 않습니다.

## 3. 무엇이 어디에 남을 수 있는가

| 자료 | 확인할 수 있는 정보 | 반드시 확인할 한계 |
|---|---|---|
| 현재 `ps` 출력 | 그 시점에 보이는 프로세스 | 이미 끝난 짧은 명령은 안 보일 수 있음 |
| 셸 history | 일부 대화형 명령 입력 | 저장 시점·설정·세션·변경 가능성, 비대화형 실행 누락 |
| 인증 로그 | 로그인·인증 관련 기록 | 모든 일반 명령 실행을 기록하지 않음 |
| systemd Journal | 기록된 시스템·서비스 메시지 | 임의의 셸 명령 stdout이 자동 보존되는 것은 아님 |
| Audit 로그 | 수집 규칙에 해당하는 행위 | 사전 규칙·권한·누락·보존 기간 확인 필요 |
| 수집한 보고서 | 조사 시점의 관찰 결과 | 원본 사건 로그가 아님, 수집자와 수집 과정도 기록 |

history를 끄거나 기록을 지우는 실습은 하지 않습니다. 로그가 비어 있는 이유를 판단하려면 수집 상태와 로깅 정책을 확인해야 합니다. 자세한 인증·Journal·Audit 분석은 후속 장에서 다룹니다.

## 4. 교육용 자료로 사실과 가설 나누기

다음은 실제 시스템에서 수집한 로그가 아니라 수업용 사실 목록입니다.

```text
case_id=LAB-001
source_type=synthetic
observed_at=2026-09-10T09:00:00+09:00
host=lab-ubuntu
uid=1000
group=sudo
approved_activity=inventory review
audit_coverage=unknown
```

좋은 분석 예:

| 관찰 사실 | 가능한 해석 | 추가 확인 |
|---|---|---|
| uid=1000 | 이 관찰 문맥의 사용자 ID | 실제·실효 ID 및 계정 기준선 |
| group=sudo | 관리자 작업과 관계될 수 있음 | 위임 정책·승인 범위 |
| approved_activity가 존재 | 정상 조사일 가능성 | 작업 시간·실행 주체 일치 여부 |
| audit_coverage=unknown | 기록 범위를 모름 | 정책·수집 상태 확인 |

잘못된 결론: “sudo 그룹이므로 root 권한을 얻었다.” 자료에는 실제 권한 변경이나 실행 결과가 없습니다.

잘못된 결론: “감사 로그가 없으므로 추가 명령을 실행하지 않았다.” 자료에는 감사 로그 자체나 기록 범위가 없습니다.

## 5. 실패를 정상으로 세지 않기

> **Bash Point — 결과 내용과 실행 상태의 분리**

```bash
if bash -c 'printf "some data\n"; exit 7'; then
    printf 'observation complete\n'
else
    status=$?
    printf 'observation incomplete: status=%s\n' "$status" >&2
fi
```

앞의 명령이 some data를 출력했더라도 결과는 incomplete입니다. 실패한 조회가 빈 출력을 냈다고 “의심 항목 0건”으로 집계하지 않습니다. 나중에 수집기를 만들 때도 `success`, `failed`, `skipped`와 각 사유를 구분합니다.

## 6. Live Response와 Offline Analysis

라이브 관찰은 변화하는 시스템에서 정보를 읽습니다. 명령 자체가 프로세스를 만들고 일부 로그·접근 시각에 영향을 줄 수 있습니다. 수집 시작·종료 사이에도 상태가 바뀔 수 있으므로 보고서를 원자적인 전체 시스템 이미지로 취급하지 않습니다.

오프라인 분석은 제공된 사본을 읽습니다. 사본의 출처·수집 시점·무결성을 확인하고 결과는 별도 위치에 저장합니다. 해시 일치는 해시를 계산한 이후의 내용 일치 여부를 돕지만, 데이터가 수집 전에 참이었는지까지 보장하지 않습니다.

이번 장의 노트북은 두 작업을 명확하게 표시합니다. **합성 자료의 고정 정답**과 **자기 환경의 가변 출력**을 같은 기준으로 채점하지 않습니다.

## 실습과 분석 질문

1. 위 사실 목록에서 확인된 사실 세 가지를 선택합니다.
2. 근거가 없는 결론 두 가지와 그 이유를 적습니다.
3. 명령 이름만으로 공격이라고 판정했을 때 생기는 오탐을 설명합니다.
4. 지금의 프로세스 목록으로 어제의 실행을 부정할 수 있는지 답합니다.
5. T1082를 적용하려면 어떤 추가 맥락이 필요한지 설명합니다.

## 완료 기준

- [ ] 사실·해석·추가 확인을 분리했습니다.
- [ ] 로그가 남기 위한 조건을 적었습니다.
- [ ] 라이브 관찰과 원본 사건 자료를 구분했습니다.
- [ ] “없음”, “미수집”, “읽기 실패”를 같은 결과로 처리하지 않았습니다.
